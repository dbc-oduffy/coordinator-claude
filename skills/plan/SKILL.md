**Trigger:** EM is about to plan implementation work where the spec carries decision weight (multi-file, new abstraction, cross-system, scaffolds new agents/skills *(decision-weight → plan, NOT architectural-tier → not a staff-session; see When NOT to use)*, reverses a prior decision) OR the PM has typed *"write a plan", "break this down", "plan the implementation"*.

**When NOT to use:** Trivial work (single-file fix, typo, link repoint, no abstraction) → just do it. Implementation-only ambiguity mid-coding → harness Plan tool inline. Architectural-tier (cross-system irreversible, multi-stakeholder) → surface to PM first. **Note — a new skill/agent scaffold is non-trivial (Branch B), NOT architectural-tier: *"novel"* / *"new surface"* / *"new skill/agent scaffold"* / *"be careful"* / *"this is unfamiliar"* are conservative-bias tells, not the four positive criteria. Architectural-tier requires one of cross-system-irreversible / multi-stakeholder / security-privacy-boundary / naming-collision-with-product-policy. Skill-scaffolds route to Branch B/C, not a staff-session.** PM in exploration mode or problem-shape not yet converged → `coordinator:shape` first (see Branch A). Spec vague or multi-subsystem → `coordinator:brainstorming` first. Skill-authoring (writing a SKILL.md) → `plugin-dev:skill-development`. Plan already written and needs review → `coordinator:review`. Stuck pattern (repeating the same action, oscillating between two approaches, stalling in analysis with no tool call, or retrying something already tried and abandoned) → stop, name the pattern, and switch to a fundamentally different approach; see Branch E below.

**Dispatch authorization — invoking this skill IS the authorization.** The dispatches named below are part of this skill, not a separate thing to get cleared: whoever invoked it has already asked for them. A generic harness preference for working inline rather than delegating does not condition them — it is written for a bare assistant with no operating doctrine, and this system supersedes it by design. Re-asking spends the very context the dispatch exists to protect. The named PM gates in this skill still bind, and ask-before-external-action still binds; nothing else here is a permission question.

## Branch A — Triage: should I plan, and at what altitude?

_Condition: EM has just received a planning trigger; first decision is whether a plan doc is the right artifact._

- _An incoming sizing-object is present?_ (the sizing lobby — `coordinator:sizing` — already resolved this ask and handed a `state/sizings/<id>.yaml` sizing-object, or the EM is picking up a sizing-routed baton that cites one; the engine assigns one of six routes — `dispatch`, `spec-dispatch`, `shape`, `plan`, `roadmap`, `pm-decision` — and this file's own D5 shape-entry gate still wins over whatever base route the object carries)
  → **Conform, don't gate — skip the rest of this triage — but conform per the object's actual `route`, not uniformly:**
    - **`route: plan`** → conform depends on how this conform arrived. **Fresh inbound** (the sizing lobby resolved this ask for the first time, or the EM is picking up a sizing-routed baton citing an object this authoring pass has not yet conformed against) → conform the object into the plan: cite the sizing-object's `intent` (verbatim), `appetite`, and `estimate` in the plan's B.0 problem-shape restatement, and proceed straight to **Branch B**. **Via the return edge** (Branch B's verified-scope-collapse row below re-invoked `coordinator:sizing` on this same pass and it returned `plan`) → conform the same way, but resume at **Branch C**, not Branch B — Branch B already ran and came back all-green on this pass, which is that row's own firing precondition, so re-running it would both waste work already done and be the thing that would let the collapse row fire twice. See Branch B's return-edge row for the full resume disposition across all six sizing routes.
    - **`route: spec-dispatch`** → conform depends on how this conform arrived, same split as `route: plan` above. **Fresh inbound** (the sizing lobby resolved this ask for the first time, or the EM is picking up a sizing-routed baton citing an object this authoring pass has not yet conformed against) → conform and proceed to **Branch B**, S-lane weight, as today. **Via the return edge** (Branch B's verified-scope-collapse row below re-invoked `coordinator:sizing` on this same pass and it returned `spec-dispatch`) → conform the same way, but resume at **Branch C**, not Branch B — Branch B already ran and came back all-green on this pass, which is that row's own firing precondition, so re-running it would both waste work already done and be the thing that would let the collapse row fire twice. See Branch B's return-edge row for the full resume disposition across all six sizing routes. In both arrival cases, the plan being authored is the **S lane**: set `scope_mode: spec-dispatch`, and the Exit below resolves the light terminal for it, not the full one. **The S lane OWES:** full Branch B substrate verification — this is precisely what makes skipping the plan review defensible, verified substrate rather than a lighter bar; B.0's `production-patch`-proportionality doubt-check (one restating sentence, not the forced-articulation triad); the concurrent-session pre-flight; the cross-plan conflict scan; and both `scaffold-plan` invocation points (scaffold, and the write-time commit — a spec that exists but is untracked nearly escapes the audit trail). **The S lane SKIPS:** Branch C's four-lens body composition (an S-lane body is four parts only — problem sentence, file scope, acceptance criteria, test surface) and the Opus plan review at Exit. **The S lane NEVER skips** scoped-commit discipline, the pre-execute authorization gate, or ask-before-external-action — a lighter lane means less ceremony, never fewer safeguards.
    - **`route: shape` / `route: roadmap` / `route: pm-decision`** → **plan is not the room.** Do not proceed into Branch B. Route to the named room instead — `coordinator:shape` for `shape`, `coordinator:roadmap-planning` for `roadmap`; for `pm-decision` there is no downstream skill to hand off to, so surface the choice directly to the PM. For `pm-decision` specifically: the engine has set the `pm_decision_pending` detent and never auto-selects an exit — the PM's pick is recorded in the sizing-object's `xl_exit` field, and a null `xl_exit` never means accept, it means the PM has not chosen yet. Name the four exits and their preconditions when presenting the choice: **`split`** — the ask decomposes into ≥2 independently-shippable pieces, each with its own acceptance criteria and no dependency on an unshipped sibling's contract (test: name piece 1 and confirm it ships alone); **`shape`** — the job-to-be-done is not stated, or the EM cannot falsifiably restate the problem in the PM's vocabulary (the same condition as this file's own D5(a)); **`roadmap`** — the work spans ≥2 named workstreams, or carries/needs an initiative/goal FK — a programme of plans, not one plan; **`accept_multi_session`** — none of the above hold (one coherent job, clear JTBD, one workstream, simply large) **and** the PM has explicitly assented — writing `xl_exit: accept_multi_session` IS that record.
  → **plan requires a sizing-object and trampolines back without one — this is a wall, not a courtesy.** The do-not-build-a-wall anti-scope ruling is deliberately lifted for `plan` alone; it continues to govern the other conform intakes (`shape`, `roadmap-planning`, `goal-setting`) unchanged. The wall here is deliberate, not an oversight — do not soften it back. The sizing-object is now a **precondition** for entering Branch B, not a receive-if-present courtesy. See the next row for the trampoline mechanism this inversion requires.
  → **What the machine actually enforces — read this before citing the wall as a safeguard that held.** Two checks exist in the control-plane engine as of 2026-08-06, and between them they catch a **wrong** citation but never a **missing** one:
    - **Write-time**, via the plan scaffolder's `--sizing-object <path>` argument: the supplied path is resolved against the repo root, and a path that does not resolve exits 1 and writes no file. Verified by execution, not by reading — a bogus `--sizing-object` run against this repo produced `error: … does not resolve on disk` and emitted no plan.
    - **Sweep**, via the engine's `assert-plan-sizing-citation` gate, run from the repo whose plans you want checked: it asserts zero dangling `sizing_object:` citations across that repo's `docs/plans/*.md`. It reads **parsed frontmatter only and never body prose** — a deliberate negative, so a plan may legitimately name a sizing object that was never written in order to *document* that absence, without a text-scanner rendering that plan unwriteable. Verified by execution against this repo's corpus: clean at exit 0, and a planted dangling frontmatter citation is caught at exit 1.
    - **The uncovered case is ABSENCE, and it is the common one.** `sizing_object:` is an optional frontmatter key, emitted only when the scaffolder is passed `--sizing-object`; no schema requires it. Omit the argument and the plan writes clean, carries no key, and the sweep — having nothing to check — reports OK. **A plan citing its sizing only in body prose is invisible to both checks by construction.** The trampoline above is the *only* thing covering absence, and it is EM behaviour plus a Stop-hook nudge (`coordinator/hooks/scripts/nudge-unrouted-sizing.py`, which fires at turn end and never intercepts the write) — not a block. Cite the wall as a rule that binds you; never as a mechanism that would have caught you.
- _No sizing-object present, and this ask has not been through the lobby — **whatever its provenance**?_ (nothing in `state/sizings/` cites it, and `coordinator:sizing` did not route it here)
  → **STOP. Do not proceed into Branch B. Invoke `coordinator:sizing` directly** — do not ask the PM's permission to size, and do not offer sizing as a question. Asking is the failure mode this row exists to kill (see the anti-gaming clause below). On return, re-enter Branch A — the conform detent above then fires, because an object now exists, so this row fires **at most once per invocation**. Dispose all six returned routes explicitly (mirror the style of Branch B's return-edge row at lines 101–106): **`plan`** → conform, proceed to Branch B as a fresh inbound; **`spec-dispatch`** → conform, Branch B at S-lane weight; **`dispatch`** → plan is not the room, abandon the pass and dispatch directly (clean by construction — `scaffold-plan` runs at Exit, so no plan artifact exists yet to unwind); **`shape`/`roadmap`** → route to the named room; **`pm-decision`** → surface the four exits to the PM. **Termination argument, stated not asserted:** the trampoline cannot ping-pong, because sizing always writes an object before returning (except the express lane — see the carve-out below), so re-entry lands on the conform detent rather than back on this row.
  - **Anti-gaming clause — this is the load-bearing part.** The gate is satisfied by **an artifact on disk in `state/sizings/` that cites this ask**, and by nothing else. It is specifically NOT satisfied by: the EM having already investigated the ask and holding the file:line substrate (knowing which files are involved is the *input* to a route, not a route); the EM having silently concluded mid-sentence that the work is multi-surface and therefore plan-tier (that is the in-head sizing the lobby exists to discharge — the table picks the room, not the EM's prior, and it may well return `spec-dispatch` rather than `plan`); or the EM asking the PM *"want me to plan that?"* (offer-and-defer is the generic-assistant turn-ending move, not doctrine — and it quietly converts a break-class finding into a PM question, which is how owning the fix gets dodged).
  - **Provenance is not the test — lobby-passage is.** This row was originally cut as *"came straight from the PM rather than through the lobby"*, which reads as a third provenance existing alongside PM-direct and lobby-routed. It does: an ask arriving via a **picked-up cross-repo memo** came from neither, and under the narrow wording it fell through the crack and was never routed to the lobby at all. A memo's `ask` is **novel work in THIS repo**, sized (if ever) by the sending EM against the *sender's* substrate — it needs the lobby exactly as much as a PM-direct ask does, and more than one that already has an object. The trampoline fires for it — under a hard gate the memo leg is trampolined, not offered.
  - **Carve-outs — exactly two, no more.**
    1. **Handoff/pickup continuation is exempt** — already sized upstream; `coordinator:sizing` is *"mutually exclusive with pickup"* on the **handoff** leg by design; see the pickup rows below, which stay unaffected by this. That mutual exclusion was never a ruling about the **memo** leg, and must not be read back onto it — a picked-up cross-repo memo needs the lobby *more*, not less (see the provenance bullet above), and under this hard gate it is trampolined, not offered.
    2. **The express lane is NOT a plan-side carve-out.** PM ruling, verbatim: *"just do it doesn't make it to planning anyway. that's an exit for the sizing lobby."* An express-lane ask terminates in dispatch at the lobby and never arrives at `plan`, so `plan` must encode no exemption for it — do not re-add one.
- _Trivial?_ (single-file change, no new abstraction, scope obvious from the ask)
  → Just do it. No plan doc. _See `coordinator/snippets/em-operating-doctrine.md` § How to Plan and Hand Off._
- _Implementation-only ambiguity?_ (multi-line edit where the EM is choosing between two equally valid shapes mid-typing)
  → Use the harness Plan tool inline. No plan doc.
- _PM has set a session axiom?_ (PM said *"we are going to do X"* / *"the next thing is Y"* / *"build Z this session"* — an explicit directive that names the work, not a question about the work)
  → Disposition default flips to **plan**, not brainstorm. The brainstorm-vs-plan triage is bypassed: the PM has already chosen scope; the EM's job is to plan the named work, not to re-litigate whether to scope it differently. Continue to **Branch B**. The architectural-tier check (final bullet) still fires — a PM axiom does not override an architectural surface-to-PM. _See § Starfleet Officer Doctrine in the global doctrine already loaded into this session._
- _The planning trigger arrived via a PM-handed pickup whose handoff prescribes a plan?_ (the PM ran `/pickup <file>` or named a handoff, and that handoff's body says "plan-shaped, not straight-to-executor", "invoke `/plan`", "decompose before executing", or equivalent)
  → **The plan is already authorized — do NOT ask "want me to plan?".** A handoff is a PM-authored artifact (only the PM creates one), so a plan trigger embedded in a PM-handed pickup satisfies the `/plan` keyword-gate transitively. Proceed into this skill directly. A T3 spinoff *fork* of the workstream stays separately PM-gated (it creates a new continuity artifact — surface it as a one-line candidate per `skills/spinoff` Step 0) but must NOT block or be conflated with the plan. _See `coordinator/snippets/em-operating-doctrine.md` § How to Decide; also `skills/pickup` Notes "T3 detection"._ Continue to **Branch B**.
- _PM in exploration mode, OR problem-shape not yet converged, OR the EM detects it is guessing at the problem?_ (open-ended framing — *"what do you think?"*, *"I'm not sure about X"*, a problem named without a deliverable; or the EM cannot confidently restate the problem the PM is solving)
  → Propose `coordinator:shape` **before** committing to plan — converge on the problem (the PRD half) first; its exit gate chains back here. This is the seam where premature convergence happens, and the EM-side complement to the global First Officer Engagement-Modes doctrine (which is personal and does not ship). **Precedence:** a PM session axiom and the architectural-tier check both take precedence — `/shape` is the exploration/unconverged-problem branch, NOT an override of a PM directive to plan named work. Discriminating test vs. brainstorming: *if the PM HAS a problem and wants confirmation you understood it (vs. not knowing what to build at all) → `coordinator:shape`, not `coordinator:brainstorming`.*
- _Cross-repo work carrying real coordination cost, even when a handoff says "ready to execute" / "investigation complete, straight execution" / "XS"?_ (it ships a cross-repo contract / hookspec / shared fixture, OR it requires sibling-EM coordination via memo + PM-relay, OR it lands in ≥2 repos whose owners must align on the shape before it can ship)
  → **Invoke `coordinator:plan` anyway — do NOT execute directly off the handoff's t-shirt.** Handoff t-shirt sizing from inside an investigation is systematically too low for cross-repo plans: investigation reveals the *structural* problem ("here's what's wrong, here's the fix shape"), but planning reveals the *implementation blast radius* (N repos, M reviewers, contract fixtures, framing-inversion checks). The two scopes are different. The handoff scope is "decide what to build"; the plan scope is "decide how it ships across N repos with M reviewers." T-shirt promotes from inside the plan body, not from inside the handoff. Continue to **Branch B**.
  - **Repo count is not the trigger — coordination cost is.** This row's evidence base is a handoff tagged XS whose real scope was 3 repos / 4 reviewers / ~2000 LOC; *"touches ≥2 repos"* was the proxy written down for it. A standing direct-commit grant makes that proxy over-fire: where one repo authors the doctrine and its engine lives in a sibling, an ordinary two-site defect fix is **one logical change at two loci** — no memo, no relay, no second reviewer, nobody to align with. **If you cannot name the coordinating party or the shared contract, this row has not fired** — size the ask on its own merits and route it like any other single-repo work.
- _Non-trivial (default for everything else)?_ (multi-file, new abstraction, cross-system, scaffolds an agent/skill, reverses prior teardown, touches shared schema)
  → Continue to **Branch B**. **Note on scope sizing:** once in Branch C, scope the task list to the COMPLETE problem set, not the slice that fits one session — see Branch C's full-coverage row.
- _Architectural-tier?_ (cross-system irreversible, multi-stakeholder, security/privacy boundary, naming-collision-with-product-policy)
  → Surface to PM: *"this looks architectural — propose `/staff-session`, want me to draft the staff-session brief?"* Wait for PM. _See `coordinator/snippets/em-operating-doctrine.md` §§ How to Decide / How to Plan and Hand Off._
  - **Non-criteria (these do NOT by themselves make work architectural-tier):** *"novel"*, *"new surface"*, *"new skill/agent scaffold"*, *"be careful"*, *"this is unfamiliar"* are conservative-bias tells, not architectural triggers. Scaffolding a new skill or agent is **non-trivial (Branch B), not architectural-tier** — the skill-scaffold checklist (Branch C) is where its risk is handled, not a staff-session. Architectural-tier requires one of the four positive criteria above (cross-system irreversible / multi-stakeholder / security-privacy boundary / naming-collision-with-product-policy). If you cannot name which of the four fires, it is not architectural — continue to Branch B. _This bullet reinforces the top-of-body When-NOT-to-use block in-tree._

## Branch B — Pre-write substrate verification

_Condition: a plan doc is the right artifact; substrate must be verified BEFORE the plan body is drafted._

### B.0 — Problem-shape confirmation (the doubt-check)

_Runs first — problem-shape is the highest substrate; verifying you understood the problem precedes verifying the file paths that solve it. This is the always-on floor that catches the case where Branch A's `/shape` offer was declined or skipped (the "just roll with it" case)._

- **A ratified problem-set exists** (a prior `/shape` ran, or `docs/problems/<slug>.md` is cited in plan frontmatter via `problem_set:`) → cite it; the doubt-check is satisfied; proceed to substrate verification.
- **No ratified problem-set, and `scope_mode` is `feature` / `architecture` / `spike`** → produce the forced-articulation block before drafting tasks (and surface its material items to the PM): **(1)** restate the problem(s) in the PM's vocabulary, falsifiably; **(2)** name your single biggest uncertainty per the un-gaming clauses below; **(3)** flag any intent you inferred that the PM did not state.
- **No ratified problem-set, but `scope_mode` is `production-patch` / `spec-dispatch` / audit (obvious one-line problem)** → the doubt-check is a single restating sentence, not the full triad. Proportional to scope — matches the coverage nudge's silence for these scope_modes, and honours P5 (`AC7`: no gate fires heavily on trivial work).

**Un-gaming clauses for step (2)** — a yes/no "I have the shape ✓" is a banned response (EM confidence is coupled with helpfulness and self-reports green every time):
1. The least-certain item must be **the scope boundary whose wrong guess would cost the most rework** ("name the boundary that, if guessed wrong, invalidates the most of the plan") — NOT "name something you're unsure about."
2. State the **probability-weighted consequence** ("if I'm wrong about X, chunks C2–C4 are rework") — a trivial selection self-evidently fails this test.
3. The surfaced uncertainty must be a **PM-altitude question** (product intent, scope boundary, success criteria). Tactical/EM-decided uncertainties (naming, test framework, commit shape, file structure) are **disqualified as off-altitude** — not merely low-stakes — regardless of how unsure you are, per `coordinator/snippets/em-operating-doctrine.md` § How to Decide. Resolving them is your job; surfacing them is noise.

_Discriminating test vs. brainstorming, if the doubt-check reveals the problem itself is unconverged:_ *if the PM HAS a problem and wants confirmation you understood it (vs. not knowing what to build at all) → `coordinator:shape`, not `coordinator:brainstorming`.*

**Known boundary:** this floor protects the plan path only. Work mis-triaged as "trivial → just do it" at Branch A bypasses both `/shape` and the doubt-check by construction — there is no floor on the just-do-it path. The mitigation is EM alertness to exploration signals at the Branch A routing row, not a second doubt-check (which would over-ceremony the trivial path, violating P5). Named here as a known boundary, not a silent one.

- _Concurrent-session pre-flight done?_ (run BEFORE scouts or reviewer dispatch — not at Branch C)
  → **Run the `concurrent-session-preflight` check** — one disk/git collision op, not two independent procedures: **(a)** today-dated-plan collision (`ls docs/plans/<today's-date>*` AND `git log --since=today --oneline -- docs/plans/`); **(b)** `source_memo:` collision, when this plan actions a cross-repo memo — i.e. it carries (or will carry) a `source_memo:` frontmatter pointer (`grep -l "source_memo:.*<memo-basename>" docs/plans/*.md` plus a body-mention fallback `grep -l "<memo-basename>" docs/plans/*.md`). Two concurrent EMs independently planning the same work is the failure mode this op exists to catch, before any scout or reviewer has spent tokens — not at the cross-plan conflict scan in Branch C (which runs after drafting). **Judgment residue (not owned by the check):** a hit on either leg is a PM-surface decision, not an automatic abort — surface the collision to the PM before proceeding. **Residual (not assumed-covered):** the `source_memo:` leg catches the plan-routed collision only; a commit-only or `inline` realization leaves no plan carrying `source_memo:`, so those collisions are caught instead by the Claim-the-memo step's memo claim-lock (while `in_progress`) and the archived `realized_by` claim-of-record (after `actioned`), not by this grep. _See `skills/pickup/SKILL.md` M3 (`realized_by`)._
- _Scope-path staleness re-check — run it at B.0 AND again immediately before the Exit's write-time commit?_
  → **The concurrent-session pre-flight above catches a competing PLAN; it does not catch competing WORK.** Its two legs grep `docs/plans/` and `source_memo:` — neither looks at the paths this plan proposes to change, so a peer session shipping the actual fix into the plan's own scope files passes it silently. Close that with two mechanical checks over the `scope:` list: `git log --since='<session start>' --oneline -- <each scope path>` for landed work, and a line-count/symbol re-read of every file the plan body cites by `file:line`. A cited line number that has moved is the cheapest available staleness signal.
  → **Re-run it at commit time, not only at B.0.** Body composition on a large plan takes long enough for a peer to land the work mid-draft, and the B.0 pass is stale by the time the plan is written. **Evidence:** an architecture-tier plan was once committed seventeen minutes after a peer session shipped a substantial part of what that plan still described as open — into the plan's own primary scope file, which had grown by over a hundred lines since the body's `file:line` citations were taken. The B.0 pass was clean and correct when it ran; nothing re-checked before the commit, so a reviewer caught it instead.
  → **When the plan's premise is "a peer team might decline X", the cross-repo memo surfaces are part of scope** — re-read `cross-repo/inbox/` and `cross-repo/archive/` for the topic before committing. An acceptance that landed mid-draft inverts the plan's stated blast radius rather than shrinking it: chunks written for the decline branch describe a shape the delivered thing deliberately does not have, and an executor handed them regresses working code back to the broken form. Pre-flight lenses do not cover this — `prior-art-checker` reads the wiki/lessons corpus and `plan-coverage-checker` reads the plan's own oracle; neither reads the inbox.
  → **Cite a peer repo's SHA as `<repo>@<sha>`, never bare.** A bare peer SHA in a plan body resolves to nothing in this tree and costs every reader an identical failed `git show`.
- _Seven-dimension confidence checklist green?_ (no-duplicate / no-fabrication / architecture-compatible / official-docs-read / reference-impl-seen / root-cause-known / fix-locus discrimination)
  → All seven green → continue to Branch C. Any red → loop back to investigation Tier 1–3 or escalate to PM.
- _Eighth dimension — unproven mechanism gate: does this plan rest on a mechanism that has not been proven viable?_
  → **This is a TYPED LOOP-BACK-TO-DERISK, not a foreign third exit — Branch B's two-valued exit invariant is preserved.** The seven-dimension checklist above still resolves to exactly two outcomes (all-green → Branch C, any-red → loop-back to investigation); this eighth dimension is evaluated alongside the seven and, on RED, resolves to the SAME loop-back outcome, specialized to a `/spike` destination rather than a generic Tier 1-3 re-investigation. Do not read this row as adding a third exit or restructuring Branch B.
  → **Before re-deriving from scratch, check for prior sizing signal:** if a sizing-object exists for this ask, read its `premise` field first — a recorded `executed` or `read` provenance there IS this eighth dimension already answered (GREEN, no re-derivation needed), while `not-applicable` or `unrecorded` leaves it to be evaluated fresh below.
  → **GREEN (no unproven mechanism):** the plan simply doesn't rest on any unproven mechanism — the common case. Nothing to cite; proceed to Branch C.
  → **GREEN (resumed from trampoline):** the plan's mechanism has already been proven by a prior `/spike` that produced a `viable` verdict for this exact mechanism — cite the `spike-result` verdict record (`docs/research/spike-verdicts/`) as evidence. Re-enter Branch C with the eighth dimension now green.
  → **RED condition: "this plan rests on an unproven mechanism gate"** — the plan's viability hinges on a mechanism (a dependency behaving a certain way, an API doing something undocumented-here, a technique nobody in this codebase has exercised) that has not been empirically demonstrated. The tell: if this dimension is RED, the natural next move would be "draft the plan anyway and let Chunk N's contingent sub-chunks handle it if the mechanism doesn't pan out" — that contingent-chunking instinct is exactly the token waste this row exists to intercept (a reviewer burns tokens reviewing chunks that may be moot). **Action on RED: trampoline to `coordinator:spike` instead of drafting contingent chunks.**
  → **Trampoline mechanism (specialized loop-back — see plan `plan⇄spike` back-edge; the spike-side half of this same edge lives in `coordinator/skills/spike/SKILL.md` § The `plan⇄spike` back-edge):**
    - **(a) Insertion point and timing.** The trampoline fires HERE, in Branch B, BEFORE Branch C body composition begins. There is no in-flight plan draft to park — Branch C has not yet run, so there is nothing to checkpoint except a *deferred plan-authoring intent*. That intent is captured in the eventual `spike-result` verdict record's (`docs/research/spike-verdicts/`) **`gated route`** field (not a plan-body stub, not a parked chunk list) — the spike-result records what plan/decision it is gating so the trampoline can be traced back to this insertion point later.
    - **(b) Dispatch.** Invoke `coordinator:spike` on the specific unproven mechanism, carrying the DEC-4 structural `trampoline: true` signal (the Branch B entry path is what supplies this signal — see `coordinator/skills/spike/SKILL.md` § Invoke Gating — DEC-4 Structural Split, Not Runtime Self-Classification). This signal is what makes the trampoline EM-reachable without a PM round-trip; a bare `/spike` invocation without it is always PM-gated, full stop — do not fabricate the signal outside this Branch B entry path.

_Condition: substrate verified; ready to draft body. The four PM doctrinal lenses bind here — this branch is where the wrong shape gets baked in._

**Lenses applied in rows 2–5 below:** time (agent-scoped only) / refactor>patch / PM-owned YAGNI / soon=now.

## Branch D — Executor BLOCKED on substrate drift

_Condition: a dispatched executor returns BLOCKED citing substrate that differs from what the plan asserted (path moved, helper renamed, framework changed, contract field absent, schema column missing)._

- _Default action: amend the plan or write a successor plan; do NOT silently expand executor scope to absorb the drift._
  → Substrate drift is plan-substrate failure, not executor failure. Re-invoke `coordinator:plan` to amend (small drift, same workstream) or compose a successor (larger drift or shape change). Re-run the prior-art-checker → the Staff Engineer → review-integrator chain on the amended body — the pipeline runs again from substrate verification, not from "we already reviewed the parent." Silently expanding the executor's scope to make the BLOCKED finding go away is a doctrine violation: it bypasses the doctrinal lenses, the prior-art check, and the reviewer pass that the original plan went through.
- _Product-risk findings during BLOCKED inspection?_
  → Even under `/autonomous`, surface product-risk findings via `AskUserQuestion` before amending. The autonomous mode suppresses handoff nudges, not product judgment. A BLOCKED that reveals (e.g.) a privacy implication, a permission default change, or an external contract shift is exactly the case the "Ask the PM" doctrine covers — autonomous mode does not waive it.

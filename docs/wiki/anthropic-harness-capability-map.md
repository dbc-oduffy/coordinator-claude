## How to use this file

Before proposing "we should adopt Anthropic feature X," check this table first. Most of the
platform docs describe **Messages API request-shape features** — fields on a raw
`POST /v1/messages` call — that Claude Code assembles internally and never exposes to a plugin,
hook, skill, or agent. A plugin author cannot set them, read them, or observe their effect. That
is not a coordinator gap to close; it is a different product surface. Citing an API doc as
justification for a coordinator feature without checking reachability here has produced dead-end
proposals before — this file exists so the next session doesn't re-derive the same negative
answer.

**Verdict legend:** **YES** — reachable today, mechanism named. **PARTIAL** — reachable only
through an indirect or narrower path than the doc describes. **NO** — API-only or product-only,
no plugin-facing lever exists. **UNKNOWN** — genuinely unsettled in the archived corpus; don't
assert either way without a fresh probe.

## What would change this map

- **A scoping miss in the original sweep — not only a version bump.** Rows were derived by
  searching the archived corpus for a *command or field name*, not for a *capability*. That framing
  routed the `/usage` row around `statusline.md`, which had documented script-readable context usage
  in the same directory the whole time. Before trusting a `NO`, re-ask it as "where can a script
  read X" rather than "does `/x` expose X." A by-capability re-ask on 2026-08-17 overturned four
  further rows (compaction, tool search, prompt caching, effort) — assume the method, not the row.
- **A page the archive doesn't have.** `env-vars.md` is cited by archived pages but is **not itself
  archived**, so every env-var verdict here rests on mentions in other pages. `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE`,
  `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`, and `ENABLE_TOOL_SEARCH` were all found that way. Archiving
  that page is the single highest-yield gap-fill.
- **A harness version bump.** This map was verified against **2.1.220**. Re-run
  `_verify-harness-capabilities.md`'s method (`claude --version`, diff against every cited
  `min-version` gate) before trusting a stale verdict on a newer install — several rows above are
  version-gated (`InstructionsLoaded`, `subagentStatusLine`) and could shift as new fields ship.
- **A new plugin-facing surface.** Several NO verdicts are NO specifically because *no plugin
  lever exists today* (prompt caching, structured outputs on the `Agent` path, batch processing).
  If Anthropic ships a plugin-facing knob for any of these, the verdict flips — check the
  changelog-equivalent (release notes / `sub-agents.md` diff) before assuming permanence.
  `tool_search_tool`/`ToolSearch` is the one live open question (UNKNOWN, not NO) most likely to
  resolve on its own with a cheap empirical probe rather than a version bump.
  See also `_mine/claude-code-product.md` § "What I looked at and found nothing in" for corpus
  areas already fully mined against current claims (`mcp.md`, `skills.md`'s `paths:`
  glob-activation — already spun off in
  `docs/plans/2026-07-27-doctrine-envelope-allocation.md`).
- **A new archived page.** This corpus has gaps it names honestly: the **Advisor tool** page was
  never fetched (`_mine/tool-use.md` item 3 — a corpus hole, not a verified NO), `settings.md` is
  a **26-line stub**, and OpenTelemetry's actual metric schema was never archived. Don't treat
  absence from this table as a settled NO for those — treat it as UNFETCHED.

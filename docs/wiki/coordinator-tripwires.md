# Coordinator Tripwires — Registry

> Registered tripwires: hooks, agent-prompt rules, and override env vars. When adding a new tripwire, register it here AND update the relevant agent prompt / hook / skill in the same commit. CLAUDE.md keeps a one-line pointer; the catalogue lives here.

- **Destructive-git orphan block (BLOCK-DESTRUCTIVE-GIT-ORPHAN):** PreToolUse(Bash) hook `block-destructive-git-orphan.sh` that re-derives true git state at the tool boundary and DENIES three commit-orphaning ops: (1) `git reset --hard <target>` when `<target>..HEAD` would drop ≥1 commit; (2) plain `git push --force`/`-f` (steers to `--force-with-lease`, which is allowed); (3) `git branch -D <name>` when `<name>`'s commits live on no other local/remote ref. Allows the benign cases (`reset --hard HEAD`/no-target, fast-forward resets, `-d`, merged-branch `-D`, bogus refs). Honors `git -C <dir>`; the `cd <dir> && git …` form is evaluated against cwd (documented v1 limitation). Override: `COORDINATOR_ALLOW_ORPHAN=1` (use ONLY after independently confirming the commits are safe — that confirmation is the point). Script: `hooks/scripts/block-destructive-git-orphan.sh`. Test: `hooks/tests/test-block-destructive-git-orphan.sh` (21 cases, real temp-repo). Origin: 2026-05-28 near-miss — an EM acting on corrupted/flaky tool output (phantom "already merged via PR#47" premise built on SHAs that never existed) proposed `git reset --hard origin/main` on a branch 257 commits AHEAD of main, which would have orphaned a day-plus of work. This hook externalizes the "verify the premise before the irreversible action" rule so it no longer depends on EM discipline or the flaky harness returning honest output. Greppable token: `BLOCK-DESTRUCTIVE-GIT-ORPHAN`.

- **Destructive-rm block (BLOCK-DESTRUCTIVE-RM):** PreToolUse(Bash) hook `block-destructive-rm.sh` — the uncommitted-work sibling of the orphan guard. Re-derives true `git status` at the tool boundary and DENIES an `rm` that would destroy work git CANNOT recover: (1) a recursive `rm` (`-r`/`-R`/`--recursive`) or a directory target that, per fresh `git status --porcelain`, holds untracked files or unstaged edits; (2) deletion of a `.git` store. Disposability is defined BY GIT — fully-committed trees pass, gitignored trees (`node_modules`/`build`/`.venv`) never appear in porcelain so they pass automatically, and targets outside any git repo pass (scratch). On top of git-disposability there is one narrow, condition-matched allowlist for **regenerable coordinator scratch**: a target is exempt from the git-status check ONLY when ALL hold — it lives at exactly `<this-repo-root>/tasks/<name>-scratch` (parent compared by inode via `-ef`, scoped to THIS repo so a sibling repo's same-named scratch does not inherit the exemption), is not a symlink, and its basename matches `^[a-zA-Z0-9_-]+-scratch$`. This closes the `/workday-complete` Step 4f case (regenerable `tasks/daily-review-scratch` tripped the guard every run) without weakening the floor: the allowlist matches *conditions*, never a broad container; preferred v2 is to relocate scratch to a gitignored path so no allowlist is needed. Allows single-file `rm` (low blast radius), `git rm` (staged, recoverable), nonexistent targets. v1 limitations: literal paths only (`$VAR`/glob skipped; `$(...)`/backtick under recursive intent fails SAFE→deny); Bash only — PowerShell `Remove-Item` is an uncovered residual (flagged to PM). Override: `COORDINATOR_ALLOW_RM=1` is read from the **hook-process environment**, NOT an inline `COORDINATOR_ALLOW_RM=1 rm …` prefix (that sets the spawned shell's env, which the hook never sees) — correct-by-design, since an inline-reachable override would let a confabulating model trivially bypass the guard on the very `rm` destroying work; the scratch allowlist removes the routine need for the override. Script: `hooks/scripts/block-destructive-rm.sh`. Test: `hooks/tests/test-block-destructive-rm.sh` (35 cases, real temp-repo). Origin: 2026-05-28 tool-output flakiness near-miss — closes the uncommitted half of the file-loss surface the orphan guard left open (diagnosis: `docs/architecture/audit-records/2026-05-29-tool-output-flakiness-diagnosis.md`). Greppable token: `BLOCK-DESTRUCTIVE-RM`.

- **Destructive-git clean block (BLOCK-DESTRUCTIVE-GIT-CLEAN):** PreToolUse(Bash) hook `block-destructive-git-clean.sh` — the uncommitted-CLEAN sibling of the rm guard (`block-destructive-rm.sh` guards `rm`/`git rm`; this guards `git clean`). Re-derives true state at the tool boundary by running `LC_ALL=C git clean -nd …` (dry-run oracle) mirroring the live command's flags; the oracle runs from the hook's own cwd (no injected `-C <repo-root>`, which would widen scope and cause false-positives on paths outside the model's working dir); it mirrors an explicit `git -C <dir> clean` when the command literally carries one. The oracle runs unconditionally — even when `clean.requireForce=false` is set — because a direct dry-run is the only reliable way to enumerate what would be removed (config knob affects the live command, not the oracle). DENIES only when the dry-run output includes a would-remove path that is under a load-bearing directory: `state/`, `docs/plans/`, `docs/decisions/`, `docs/wiki/`, `docs/research/`, `cross-repo/inbox/`, `cross-repo/archive/`, `cross-repo/outbox/`, or a path whose basename matches a completion/handoff/review glob (`*handoff*.md`, `*completion*.md`, `*review-trail*`). This is an INTERSECTION check — a load-bearing-path hit PLUS untracked AND would-remove — NOT a blanket deny on every `git clean`. Allows: dry-run invocations (`-n`/`--dry-run`) — these are safe and used by the oracle itself; cleans whose dry-run output hits only disposable/scratch/gitignored paths (e.g. `build/`, `node_modules/`, `.venv/`); scoped `-- pathspec` cleans that resolve to non-load-bearing targets; `git clean` invoked outside any git repository. If the oracle subprocess times out or fails, the hook DENIES fail-closed. v1 limitations: command-position only — a `git clean` following a `&&`/`;` segment is matched but pathspec arguments are parsed from the literal command text; `$VAR`/glob pathspecs are not shell-expanded before the dry-run, so unusual pathspec forms may be under-evaluated (the dry-run itself is always literal); a `cd <dir> && git clean` form is evaluated against the hook's own cwd, NOT the cd target (v1 limitation, parity with block-destructive-rm.sh's cd limitation); PowerShell `git clean` invocations are uncovered. Override: `COORDINATOR_OVERRIDE_GIT_CLEAN=1` from the **hook-process environment** (NOT an inline prefix — a confabulating model cannot trivially bypass the guard via inline-prefix; the env var must be present at hook time, set by the human or a trusted parent process). Script: `hooks/scripts/block-destructive-git-clean.sh`. Test: `hooks/tests/test-block-destructive-git-clean.sh`. Origin: 2026-06-30 project-rag incident — a sibling session's `git clean -fd` destroyed 8 untracked spinoff handoffs mid-`/workstream-complete` ceremony; state was irrecoverable (no commit, no stash, no reflog). Greppable token: `BLOCK-DESTRUCTIVE-GIT-CLEAN`.

- **Destructive-git revert block (BLOCK-DESTRUCTIVE-GIT-REVERT):** PreToolUse(Bash) hook `block-destructive-git-revert.sh` — the fourth leg of the destructive-git safety floor, closing the "uncommitted-tracked-REVERT + untracked-sweep" loss class the other three siblings do not cover: `block-destructive-git-orphan.sh` only denies commit-DROPPING resets/force-pushes/branch-deletes, so a same-branch whole-tree `git checkout .` / `git restore .` / `git reset --hard HEAD` (which drops zero commits) sails through untouched, and it is DIFFERENT from `block-destructive-rm.sh`/`block-destructive-git-clean.sh` because it discards unstaged edits to TRACKED files (not `rm`-deleted trees or untracked-only clean sweeps) — a loss class that lives in no commit, no stash, no reflog. DENIES four covered forms, each re-derived from a fresh `git status --porcelain` oracle at the tool boundary: (1) whole-tree `git checkout .`/`git checkout -- .`/`git checkout HEAD .`/`git checkout HEAD -- .`/`git checkout <ref> -- .` (pathspec must be literally `.`; a branch switch or a scoped `git checkout -- <path>` is NOT matched); (2) whole-tree `git restore .`/`git restore -- .`/`git restore --worktree .`/`git restore -W .` (working-tree targeted, pathspec `.`) — `git restore --staged .` with no `-W`/`--worktree` does NOT touch the working tree and is explicitly ALLOWED (non-destructive); (3) `git reset --hard` with no pathspec (git rejects `--hard` + a pathspec, so this is the only reachable form; independent of and running AFTER the orphan guard in first-deny-wins order — the orphan guard denies first on any commit-dropping reset, this hook catches the uncommitted-hunk loss on a same-branch reset the orphan guard lets through); (4) unscoped `git stash`/`git stash push`/`git stash save` with `-u`/`--include-untracked`/`-a`/`--all` and NO `-- <pathspec>` (a SCOPED `git stash push -u -- <paths>` is NOT matched — that is the safe form the sibling guards already recommend). **Precision gate (the offer, not a nag, mechanism):** the oracle's affected-path set is classified as LOAD-BEARING (two-direction ancestor check against `state/`, `docs/plans/`, `docs/decisions/`, `docs/wiki/`, `docs/research/`, `cross-repo/{inbox,archive,outbox}/`, handoff/completion/review-trail globs — `_gr_LOADBEARING_RE`/`_gr_LOADBEARING_PREFIXES`, copied from `block-destructive-git-clean.sh`'s classifier with `_gr_` names so the hook is self-contained standalone) OR PEER-CLAIMED (copied `_rm_peer_claim_of` logic from `block-destructive-rm.sh` as `_gr_peer_claim_of`, un-overridable when a LIVE peer session's `touched.txt` claims the affected path in the shared worktree). DENY fires iff ≥1 affected path is load-bearing OR peer-claimed; otherwise ALLOW — an operator discarding their own disposable, uncontested WIP is left alone. Fail-safe direction: not-a-repo/git-error oracle failures ALLOW silently (nothing to lose); an oracle that reported affected paths but could not classify them due to missing tooling fails SAFE toward DENY (mirrors the clean guard's timeout-deny posture). Override: `COORDINATOR_OVERRIDE_GIT_REVERT=1` from the **hook-process environment** (NOT an inline prefix), honored early before the oracle runs. Script: `hooks/scripts/block-destructive-git-revert.sh`. Test: `hooks/tests/test-block-destructive-git-revert.sh` (31 cases, real temp-repo). Origin: 2026-07-10 accepted cross-repo memo (project-rag) — a sibling session on a shared `work/*` tree ran `git checkout .` which reverted tracked-but-uncommitted hunks in shared files (registry, pyproject, golden fixtures, wiki), a live peer's reviewed-and-ready work, git-unrecoverable because unstaged edits to tracked files live in no git object. Greppable token: `BLOCK-DESTRUCTIVE-GIT-REVERT`.

- **BLOCK-BLANKET-GIT-ADD:** PreToolUse(Bash) hook `block-blanket-git-add.sh`, registered in `hooks/hooks.json` alongside `block-destructive-rm.sh`. Fires only when cwd is inside the `~/.claude` meta-repo (inode-equality via `git rev-parse --show-toplevel` `-ef` compare to `$HOME/.claude`). **Origin incident:** 2026-06-15 — 4 cross-contamination commits in one day on `work/striker/2026-06-14` (commits `2cae346f`, `7e404514`, `d58a7721`, plus one morning instance); sibling sessions ran `git add -A` and silently absorbed in-flight uncommitted work from concurrent sessions into commits whose subjects described unrelated workstreams. **Pattern:** blocks blanket-add forms in any segment of a chained command (segment-split per `block-destructive-rm.sh:131-135`): `git add -A`, `git add --all`, `git add .`, `git add ./`, `git add -u`, `git add --update`, bundled short-flags `-An`/`-Av`/`-fA`/`-Au`/`-uA`, and `git add -A --` followed by path. **Override (env-only, NOT inline prefix):** `COORDINATOR_OVERRIDE_BLANKET_ADD=1` in the hook-process environment. An inline prefix `COORDINATOR_OVERRIDE_BLANKET_ADD=1 git add -A` sets the spawned shell's env, which the hook never sees — correct-by-design (a confabulating model cannot trivially bypass the guard). **Helper bypass (internal-only):** `_COORDINATOR_SAFE_COMMIT_INTERNAL_BLANKET=1` is set by `coordinator-safe-commit`'s `do_blanket` and `do_override` paths around their sanctioned `git add -A` calls (the helper's marker env var; see `bin/coordinator-safe-commit:743,1043`). **v1 limitations:** command-substitution (`git add $(echo -A)`), variable-expansion (`git add $FLAG`), and here-doc bodies textually containing `git add -A` pass through (documented in hook header; mirrors `block-destructive-rm.sh:46-48`). Test file: `plugins/coordinator/bin/tests/test-block-blanket-git-add.sh`. Plan: `docs/plans/2026-06-15-harden-safe-commit-against-sibling-add-all.md`. Doctrine: SC-DR-014 (unambiguous-command-class carve-out from Phase-5 soak gate); SC-DR-008 (plain `git add -- <paths>` is the default for scoped commits). Greppable token: `BLOCK-BLANKET-GIT-ADD`.

- **Git-C-over-cd offer (OFFER-GIT-C-OVER-CD):** PreToolUse(Bash) hook `offer-git-c-over-cd.sh` — a low-stakes REDIRECT, not a destructive guard. Fires ONLY when the first command segment is `cd <path>` AND the second is a `git` invocation. Rationale: a leading `cd` makes a compound command that trips a permission prompt rendering as a non-returning `Waiting…` — the stall misread as a flaky channel that drove the 2026-05-30 probe-spray loop (`echo ALIVE`/`printf CHAN_OK`/variant `git log`, broken only by PM interrupt). `git -C` is the exact, prompt-free equivalent. **Three-tier response (v3, 2026-07-02):** (1) clean 2-segment `cd X && git Y` → TRANSPARENT AUTO-REWRITE via `updatedInput.command` (allow, no friction); (2) redundant cd with followers where X resolves to the current cwd → AUTO-REWRITE by stripping the leading `cd X` (allow, no friction); (3) non-redundant cd with cwd-dependent followers → DENY with the `git -C` suggestion and a cwd-binding note explaining that followers no longer run in X. Fail-open: missing cwd or unresolvable path falls through to tier 3. Deliberately narrow: `cd X && npm i && git status` (second segment not git), a mid-chain `cd` (`ls && cd X && git …`), and `cd X && <non-git>` are all left alone. Does NOT cover the OTHER wiki-named trigger — batched redundant variant-probes across sibling tool calls — because a per-call PreToolUse hook cannot see the batch; that stays doctrine-only. Override: `COORDINATOR_ALLOW_CD_PREFIX=1` from the **hook-process environment** (an inline prefix sets the cd child's env, which the hook never sees). Script: `hooks/scripts/offer-git-c-over-cd.sh`. Test: `hooks/tests/test-offer-git-c-over-cd.sh`. Splits only on `&&`/`;`/newline (not `|`/`||`/`&`), bails on cd flag/special-forms (`-`, `-L`, `-P`, `--`), and bails on an unbalanced quote in a segment (a `&&`/`;` inside a quoted git arg) so the rewrite is never malformed. Doctrine: `docs/wiki/tool-output-flakiness-protocol.md` § Not this protocol — blocked / no-return. Greppable token: `OFFER-GIT-C-OVER-CD`.

- **Probe-spray nudge (NUDGE-PROBE-SPRAY):** PreToolUse(Bash) hook `nudge-probe-spray.sh` — offer-shaped, **warn never block** (allow + additionalContext). Catches trigger 2 of the blocked/no-return failure: after an empty/`(No output)`/non-returning result the model sprays liveness probes (`echo probe`/`echo ping`/`printf CHAN_OK`/`sleep 1; echo done`/repeated `git log -1`) that diagnose nothing. Defeats the "a per-call hook can't see the batch" objection with DISK STATE — a session-keyed rolling window (`$TMPDIR/coordinator-probe-spray-<session>.*`) counts probe-shaped commands; at ≥3 within 90s it nudges once (30s cooldown so the nudge isn't itself spam), and any clearly-real command resets the streak. Probe shapes: `echo <single-token>` (bare OR quoted — the real shape is `echo "se-flush-3"`), bare `echo`/`true`/`false`/`:`/`pwd`/`date` no-ops, short `printf` literal, `sleep N`, or a command whose hash recurs ≥2× within a small ring (catches alternating/repeated re-reads while giving legitimately-repeated real commands like `make` latitude). Keyed by `session_id` from the hook's stdin payload (stable across a session) → `CLAUDE_SESSION_ID` → `$PPID`. A single legitimate echo/sleep never nudges. Off switch: `COORDINATOR_PROBE_NUDGE_OFF=1` (echo/sleep-heavy autonomous runs). Script: `hooks/scripts/nudge-probe-spray.sh`. ## Override Flags as Latent-Rot Signal

Safety-gate failures that surface when an override flag is used can be latent-broken since the gate was authored. When a check or probe is guarded by an override flag, the flag's existence is a smoke signal — not evidence that the gate works when the flag is absent. Before reaching for an override, read the probe's actual code and verify that the no-override path behaves as documented on the current substrate.

Specifically: a probe that was written against an older install shape, a probe whose sentinel file never gets created on clean installs, or a probe with a syntax error in its main body will all "work" (silently pass or error-suppress) under the override while being completely broken in the default path. The pattern is: gate was added → subsequent install-surface change made the gate's logic wrong → override was added "temporarily" → override became permanent → gate is now theater.

**Rule:** any use of an override env var for a safety gate requires reading the gate's source before invoking the override — not after, not as a follow-up. If the gate is genuinely broken, fix it or remove it; if it's correct, the override is not needed. Override-and-continue is only legitimate when the override's semantics match the actual situation (e.g., `COORDINATOR_OVERRIDE_ACCEPTANCE_GATE=1` when the host topology genuinely cannot reproduce the AC environment). (Source: 2026-05-24 project-rag-ue-addon)

## Existence-checks are not behavior-gates — pair with `bash -n`

A tripwire battery that asks "does the file exist?" and "does the registry list it?" does NOT answer "does this script parse?" or "does it run?". A probe/helper shell script that crashes at line 1 satisfies every existence / inventory / verdict-lint tripwire while delivering zero diagnostic value — every wrong path is non-empty, it just points at nothing. Two 2026-05-21 instances: doctor probes shipped with invalid here-doc syntax (unterminated `<<'PYEOF'`) and an `Accept: application/json` header against an SSE endpoint, all green on the existence battery.

**The cheap floor is `bash -n`** (syntax-only, zero runtime cost) across `commands/lib/**.sh` and `**/probe-*.sh` — it would have caught the parse error. Runtime coverage (probe-against-live-daemon smoke at session-end / workday-start) catches the protocol-shape class but is heavier. Add the `bash -n` floor to CI for any agent-facing diagnostic tool whose substrate is shell scripts; the existence-check anti-pattern generalizes anywhere a tripwire asserts *presence* rather than *behavior*. Pairs with the wiring-layer-conformance lesson — file-level conformance ≠ runtime registration. (And note the CRLF caveat: on a Windows working tree with `core.autocrlf=true`, `bash -n` itself false-positives on heredoc-heavy scripts — see `claude-code-platform-gotchas.md` § Windows bash / CRLF; ShellCheck is the real lint.)

## Complete-the-set actions don't need PM-which-one calibration

When an action set is **bounded and cost-symmetric** (each item costs roughly the same, there's a finite known list, and doing all of them is not riskier than doing one), bias to **do-all** rather than do-1/N-and-ask-about-the-rest. Asking "should I also do the other N−1?" is false-choice ceremony when the subset is bounded and the per-item cost is symmetric — the EM owns that call. This extends the `CLAUDE.md` § Challenging the PM "Don't ask for" list: completing a bounded symmetric set is a routine implementation choice, not a product decision. (PM-which-one calibration is still right when items have *asymmetric* cost or visible-behavior divergence — then the choice is a real fork.)

## Don't queue PM questions behind unrelated blockers

Each PM question lands on its own timeline — do not batch a ready-to-ask question behind an unrelated blocked one ("I'll ask about X once Y resolves"). Blocking a clear question on an unrelated blocker silently delays a decision the PM could make now, and the two timelines have no real dependency. Surface each question when it's ready; don't conflate "these came up in the same session" with "these must be answered together."

## Ship-and-watch telemetry needs a calendared review or a hard tripwire — no third option

When you ship instrumentation/telemetry to "watch and see," there are exactly two legitimate dispositions: (a) a **calendared review** (a dated marker file or recheck that forces someone to look at the data), or (b) a **hard tripwire** (a gate that fires automatically on the measured condition). The third option — ship-and-passively-watch with no forcing function — is the failure mode: nobody looks, the telemetry rots, and the measurement question goes unanswered. Additionally, the **measurement filter must match the doctrine's enumerated target set** — a telemetry probe that measures a broader or different population than the doctrine targets produces data that can't answer the question (the tier-usage telemetry removed 2026-05-18 is the canonical miss: it conflated investigation scouts with the whole `Agent` surface).

## doc-link-checker adds no signal on private-repo absolute self-URLs

The `doc-link-checker` worker (→ `CLAUDE.md` § Reviewer-Routed Workers) cannot verify absolute URLs into private repositories — a GitHub URL pointing at a private repo returns 404 to the checker regardless of validity, producing false-negative noise. **Gate doc-link-checker dispatch on relative-link and public-URL presence**: if a diff's links are all private-repo absolute self-URLs, the checker adds no signal and should be skipped. Route it when there are relative links (resolvable on disk) or public URLs (resolvable over the network) to verify.

## Confirm peer-EM deployment-topology premise with PM at /shape before the pipeline

When a peer-EM recommendation (inbound memo, cross-repo brief) bakes in a **deployment-topology premise** — "both repos ship together," "the consumer runs on the same host," "this is one install surface" — confirm that premise with the PM at `/shape` *before* spinning up the full plan → review → cross-repo-contract pipeline. The topology premise determines whether the work is one coordinated change or two independent ones; getting it wrong means the entire pipeline runs against the wrong shape. This is a `/shape`-altitude convergence question (does the EM understand the deployment topology the same way the PM and peer-EM do?), not something to assume from the memo's framing. → `CLAUDE.md` § Challenging the PM; pairs with `cross-repo-communication.md` § "Memo framing is hypothesis at the architectural altitude too."

## Line-number-keyed allow-lists drift under concurrent multi-session edits

Any allow-list / suppression-list / sidecar that keys entries by **line number** (`filepath:42`, "suppress the finding at line 118") drifts the moment a concurrent session edits the file above that line — the line moves, the key now points at the wrong line, and the suppression either misfires or silently stops applying. Under the shared-workstream-branch model (multiple EM sessions editing the same tree), line-number keys are structurally fragile. **Key on a stable marker instead**: an anchor heading, a unique token in the line, a `# noqa: <rule>` inline comment, or a content hash — anything that survives line-number shift. This is the same failure class as the cross-repo "Four coupled path declarations" lockstep problem, applied to suppression keys.

## ~/.claude/ is a git repo — orphan audits must check git remote + ls-files first

`~/.claude/` (Claude Central / Claude Prime) is itself a git repository with a remote. Any audit that classifies files under `~/.claude/` as "orphans" / "untracked debris" / "candidates for deletion" MUST first run `git -C ~/.claude remote -v` and `git -C ~/.claude ls-files <path>` to check whether the file is tracked and pushed. A file that looks like a stray local artifact may be a committed, remote-backed part of the meta-repo. Classifying tracked-and-pushed content as an orphan and deleting it is data loss masquerading as cleanup. The git remote + ls-files check is the cheap floor before any orphan-deletion call on `~/.claude/` contents.

## Shared-substrate doctrine — distinguish schema-authorship from value-writing

For any registry, schema, or on-disk format that multiple agents/repos read and write, **distinguish who authors the schema (the format owner) from who writes values into it (the contributors)**, or expect sidecar defections. When the two roles are conflated — "whoever needs a field just adds it" — contributors who can't get their field into the shared schema cleanly defect to their own sidecar files, and the shared substrate fragments into N parallel formats. This is the library-vs-service substrate question: a *library* substrate lets any consumer author values against a stable schema owned by one party; a *service* substrate mediates all writes through an owner. Decide which shape the substrate is and name the schema-owner explicitly. ## MEMO-PREDISPATCH-STANDDOWN

**Anti-pattern:** dispatching an executor (or otherwise performing the work) on an accepted memo `ask` without first running the M3 Accept pre-dispatch reconcile (`git fetch` + re-read the memo's own `status:`/`picked_up_by:`, plus the positive-liveness reconcile on the memo's topic nouns). The `cs_claim_memo` `mkdir` claim lock is machine-local — invisible to a second machine on the shared `work/*` branch — so skipping the reconcile means the only honest cross-machine signal (committed `picked_up_by:`/`status:` frontmatter) is never checked immediately before dispatch. Result: cross-machine duplicate pipeline spend — a peer that claimed-and-pushed since the M2.5 fetch goes undetected, and both machines run a full executor → code-reviewer → review-integrator pipeline on the identical change.

**Fix:** run the M3 Accept pre-dispatch reconcile immediately before "perform the work / dispatch an executor": (1) fetch + re-read frontmatter; (2) run the canonical positive-liveness predicate (§ Routed-plan reconcile-and-surface — active handoff / live `cs_claim_holder_live` claim / live Dispatch-Ledger rows + commit within 24h) against the memo's topic nouns; (3) any peer signal fires → surface `"peer may be live on <memo topic> — verify before dispatching"` and **stand down** until the operator confirms the peer is gone. This is a stand-down/reconcile, not a hard block — the residual race is bounded to duplicate spend, never incorrect state (the `open → actioned` terminal flip remains the cross-machine coordination primitive). A `git fetch` failure must surface `"could not fetch peer state — cross-machine liveness unverified"` and stand down rather than silently proceeding as if the fetch succeeded.

**Enforcing surface:** `skills/pickup/SKILL.md` M3 **Accept** § Pre-dispatch reconcile (doctrine prose — the memo-branch analog of the handoff-side Step-3.4h stand-down, which is itself prose, not a hook). **Origin:** 2026-07-08 example-orchestration-hub near-miss — two machines on the shared `work/*` branch picked up the same `ask` near-simultaneously; both ran full pipelines on the identical change. Spec: `docs/plans/2026-07-09-continuity-artifact-staleness-parity.md` Fix #1.

**Anti-pattern:** a `status: draft` plan sitting in `docs/plans/` for 14+ days with no recent real-work commit and no owning baton, going unnoticed because nothing surfaces it — the same "silent staleness" failure mode `handoff-gate-aging.sh` addresses for handoffs, applied to draft plans.

**Predicate (surface-not-delete):** `coordinator/bin/draft-plan-aging.sh` flags a plan STALE iff ALL hold: (1) `status: draft`; (2) `now - created: >= 14 days`; (3) no commit within the aging window on a normalized scope path whose subject is off the mechanical denylist (`pickup:`/`reclaim(docs)`/`session-init`/`frontmatter mutation`), AND no non-`consumed` handoff in `state/handoffs/*.md` references the plan's on-disk path (active baton). A no-scope plan fails condition 3 definitionally — toward surfacing, never a silent pass. The script only detects and reports (stdout lines + 0/1/2 exit contract); it never deletes, archives, or mutates the plan — the caller (`/workday-start`, `/workweek-start`) drives the decision prompt (execute / archive / close-DR), and the actual disposition is always an explicit PM/EM call, not automated.

**Enforcing surface:** wired into `/workday-start` Step 1.2 ("Mechanized draft-plan staleness check") and `/workweek-start` Step 3 item 2, both running `coordinator/bin/draft-plan-aging.sh docs/plans` unconditionally. Exit `1` surfaces the flagged plans under a "Stale draft plans" subsection with a decision prompt; exit `2` surfaces the stderr diagnostic verbatim under the same subsection — do not silently drop the malformed record.

**Origin:** `docs/plans/2026-07-09-continuity-artifact-staleness-parity.md` § Design Fix #2 (draft-plan liveness detector, faithful clone of `handoff-gate-aging.sh`'s structure).

Greppable token: `DRAFT-PLAN-AGING`.

- **Plan-tasks deferral harvest (PLAN-TASKS-DEFERRAL-HARVEST):** [universal] The task-spine contract — every plan's `## Tasks` section carries EXACTLY ONE fenced ```` ```yaml plan-tasks``` ```` block directly under the heading (a YAML list of task-row objects: `id`, `title`, `change_kind`, `surface`, `queue_scope`, `deferred`, `pm_approved`, `body`) — is the SSOT parsed by `coordinator/schemas/plan-tasks.schema.json`, the plan-coverage-checker (fails loud on zero/>1 fenced blocks — it cannot do its job without the spine), and the harvest mechanism below (warns-and-skips on the same condition — a plan mid-authoring may not have a spine yet). Rows with BOTH `deferred: true` AND `pm_approved: true` are harvest candidates — a PM-ratified scope cut, never an EM preference alone. **Harvest mechanism:** `coordinator/bin/coordinator-harvest-deferrals --plan <plan-path> [--dry-run]` parses the spine, selects candidate rows, and routes each by `change_kind` — the 8-value project-tier improvement-queue-eligible subset (`script-edit`, `skill-edit`, `wiki-append`, `wiki-new`, `hook-edit`, `agent-prompt-edit`, `doc-edit`, `test-edit`) goes to `coordinator-queue-append --schema improvement-queue --queue-scope <row's queue_scope, default project> --status open`; the doctrine-class subset (`doctrine-edit`, `snippet-sync-update`, rejected by improvement-queue at project scope) goes to `coordinator-lesson-promote`. **Idempotency:** keyed on `(plan_id, row id)` — combined into a `harvest-key: <plan_id>:<row id>` string embedded in the written entry's `evidence:` field; before writing, the script text-scans the target directories' `*.yaml` files' `evidence:` fields for that exact key and skips on a match. This idempotency is what makes it safe to harvest the same plan more than once across its lifecycle. **Two call-sites, by design, both relying on the same idempotency guarantee:** (1) `coordinator:execute-plan` Phase 1.6 — harvests deferrals visible at plan-mapping time, before any chunk dispatches; (2) `/workstream-complete` Step 2.4b (belt-and-suspenders sweep, same governing-plan predicate as Step 2.4) — re-runs the identical harvest at workstream wrap, catching deferrals that flipped to `deferred: true && pm_approved: true` *during* execution (a chunk executor hits a structural blocker mid-flight, or the PM ratifies a scope cut mid-wave) that Phase 1.6 could not have seen. The second call is a superset re-run, not a distinct mechanism — rows Phase 1.6 already harvested are silently deduped (surfaced as "already-harvested," never re-queued); only newly-flipped rows are freshly harvested. Malformed rows (missing required field, or the block fails `yaml.safe_load`) are SKIPPED-WITH-WARNING by the harvest (defensive parse-or-skip) and FLAGGED by the coverage-checker (the enforcement surface) — the two tools have deliberately different failure postures for the same malformed-row condition. **Contact-points:** `coordinator/schemas/plan-tasks.schema.json` (spine schema SSOT), `coordinator/bin/coordinator-harvest-deferrals` (harvest CLI), `skills/execute-plan/SKILL.md` Phase 1.6 (map-time call-site), `skills/workstream-complete/SKILL.md` Step 2.4b (wrap-time call-site), plan-coverage-checker (spine-absence fail-loud consumer). - **Live Bash-matcher hook edit discipline (LIVE-HOOK-EDIT):** Process/discipline entry, not a mechanical PreToolUse gate — there is no reliable way to intercept "an Edit tool call targeting a currently-registered hook path" without also blocking legitimate hook maintenance, so this ships as a design-as-offer convention rather than a hard block.
